Executive summary

This review was triggered by the Coldcard seed-generation failure (Coinkite advisory, 30–31 July 2026): a 2021 refactor silently bound seed generation to MicroPython's software PRNG instead of the hardware RNG — the two functions shared a name, the build picked the wrong one, and nothing runtime-checked the result. Mk3 seeds carried ≈40 bits of entropy; ≈594 BTC was swept from ≈500 wallets. We audited Trezor Safe 7 and BitBox02 for the same bug class and for the wider set of custody-breaking risks.

Headline verdict: neither device carries the Coldcard bug, and both are structurally immune to it. Seed entropy on both devices XOR-combines multiple physically independent sources, so no single failed or mis-linked source can determine the seed; all hard-failure paths fail closed (hang/exception/abort), never degrade silently. The Trezor same-symbol weak/strong RNG pattern that doomed Coldcard exists in Trezor's tree but is fenced by four independent build-time guards; BitBox02's fake/real RNG swap is structurally impossible to mis-link.

1 · The Coldcard baseline: five failure modes

Per Coinkite's advisory and incident reporting (July 2026): during the 2021 migration to Bitcoin Core's libsecp256k1, Coldcard's seed generation began calling MicroPython's software PRNG instead of the hardware RNG — both functions had the same name, and the build silently selected the wrong implementation. Wallets displayed perfectly valid 24-word phrases. Mk3 (single source): ≈40-bit effective entropy. Mk4/Mk5/Q: ≈72 bits, saved from total collapse only because their two secure elements still contributed. Fixes shipped in Mk3 4.2.0+, Mk4/Mk5 5.6.0+, Q 1.5.0Q+ — but already-generated seeds are permanently weak; users must migrate.

FMFailure modeAudit question for Trezor / BitBox02
FM1Same-symbol weak/strong RNG → silent wrong binding at link timeCan a weak PRNG object/module silently replace the strong one in a production build?
FM2No runtime health test on entropy sourcesWould a stuck/constant/degraded TRNG be detected at runtime?
FM3Single-source dependency (no defense-in-depth mixing)Can one source's failure determine the seed?
FM4Failure paths continue with degraded entropyDoes any error path fall back to weaker randomness instead of halting?
FM5No verification that external entropy was honestly incorporatedCan the host verify the device mixed in contributed entropy?

2 · Entropy architecture review

2.1 Trezor Safe 7 (T3W1 — STM32U5 + Optiga Trust M + TROPIC01)

Seed entropy flow: reset_device/__init__.py:88 → random.bytes(32, strong=True) → rng_fill_buffer_strong() → per-32-byte-block XOR of STM32 TRNG ⊕ Optiga ⊕ TROPIC01 (core/embed/sec/rng/rng_strong.c:38-72) → SHA256(int_entropy ‖ host_ext_entropy) under an HMAC commitment, with an optional host-driven entropy-check protocol that re-derives xpubs to prove honest mixing (reset_device/__init__.py:92-105, 343-356).

bool rng_fill_buffer_strong(void* buffer, size_t buffer_size) {
  rng_fill_buffer(buffer, buffer_size);          // MCU TRNG first
  ...
  while (remaining > 0) {
    if (!optiga_random_buffer(block, block_size)) { return false; }  // fail closed
    for (i...) dst[i] ^= block[i];
    if (!tropic_random_buffer(block, block_size)) { return false; }  // fail closed
    for (i...) dst[i] ^= block[i];
  }
  return true;
}

2.2 BitBox02 (SAMD51 + ATECC608B; Nova: SAMD51 + Optiga Trust M V3)

Seed entropy flow (keystore.rs:577-608):

seed = SHA256(MCU_TRNG ⊕ SecureChip_TRNG ⊕ FactoryRandom)[:n]   // bitbox-core-utils/src/random.rs:9-30
     ⊕ HostEntropy[:n]                                            // mandatory, 16/32 B — set_password.rs:23-25
     ⊕ SHA256(salt ‖ "keystore_seed_generation" ‖ password)[:n]

Five independent contributions; host entropy XORed post-hash so it can only add entropy; seed stored AES-256-CBC+HMAC under a secure-chip-stretched key, read back and verified after write (keystore.rs:354-367), BIP39 seed derived twice and compared at unlock (fault check, keystore.rs:534-542).

H1 — Downgrade/rollback: Refuted for both

Correction: the interim assessment ("no anti-rollback on either device") was wrong. Both implement hard monotonic downgrade protection; this matters precisely because a rollback-to-vulnerable-firmware attack is the exploitation path for entropy bugs like Coldcard's.

Trezor ✔

  • Hard monotonic counters in one-way MCU state (OTP bits on F4; zero-only blocks in secure flash on U5, max 63): bootloader/version_check.c:26-60 — separate counters for firmware, bootloader, secmon.
  • Enforced at upload (wf_firmware_update.c:257-261) and at every boot (fw_check.c:97,149; main.c:445-481).
  • Residuals: floors move only when SatoshiLabs bumps FIRMWARE_MONOTONIC_VERSION (currently just 1–2 across models — few historical releases are actually blocked); SEs don't participate; same-monotonic downgrade allowed but wipes storage below fix_version.
  • Exception: legacy Trezor One — wipe-only, no blocking (legacy/bootloader/usb.c:188-205).

BitBox02 ✔

  • Monotonic floor in bootdata: bootloader.c:655-658 (version_new < stored → ERR_VERSION); version inside the signed preimage (:551-564); bootdata written only by bootloader, MPU-blocked from firmware (mpu_regions.c:88-94); stage1 has its own monotonic (stage0.c:628-635).
  • Flashing does not wipe the seed; entry to bootloader requires on-device confirmation.
  • Residuals: same-version reflash allowed; factory-fresh devices have floor 0 (any historical signed firmware loads); floor resets if bootdata's 2 init bytes are corrupted (bootloader.c:940-946) — fault-injection-grade edge.

H2 — Nonce exfiltration: Trezor confirmed / BitBox02 partial

Trezor ✔ — no anti-exfil defense exists

  • Zero anti-exfil/sign-to-contract code anywhere (double-grepped); signing API takes no host-nonce input (crypto/ecdsa.h:98).
  • ECDSA = pure RFC6979, NULL extra data on first attempt (zkp_ecdsa.c:220-232).
  • BIP340/Schnorr aux_rand = NULL (zeros) at every call site (modtrezorcrypto-bip340.h:106-108) → taproot signatures fully deterministic.
  • No verify-after-sign anywhere — a glitch mid-scalar_multiply could return a key-leaking (r,s) pair unchecked (ecdsa.c:707-773, zkp_ecdsa.c:207-262).
  • Defense rests entirely on supply chain (H1) + reproducible builds — which are strong, but there is no protocol-level tripwire.

BitBox02 ✔ — real coverage, real gaps

  • Anti-klepto primitive verified: host nonce mixed into RFC6979 + signer-commitment round-trip (bitbox-secp256k1/src/lib.rs:129-192); engaged on BTC ECDSA, BTC signmsg, ETH sign/signmsg/EIP-712 whenever the host commits.
  • Taproot hard gap: signtx.rs:1210-1213 — "Anti-Klepto protocol not supported yet for Schnorr signatures"; host commitment → InvalidInput. Schnorr nonce = device aux_rand only (from the full mix).
  • Optional everywhere: host omitting the commitment gets a signature anyway via zero-host-nonce fallback (signtx.rs:1295-1319) or plain RFC6979 (EIP-712). Only hosts that require the commitment round-trip are protected; the reference client does by default.
  • Not covered: Cardano (ed25519, deterministic — limited channel), U2F (secure-chip internal).

H3 — Brute force: Refuted for both

  • Trezor: 10 tries (Tropic models incl. Safe 7) / 16, then wipe (storage.h:44-55); counter pre-incremented in flash with verified increment + guard-bit tamper checks (storage.c:1217-1229); exponential backoff 2ⁿ−1s; Optiga hardware attempt counter + TROPIC01 mac-and-destroy slots consumed per attempt (tropic.c:1252-1298).
  • BitBox02: 10 attempts → full seed wipe (keystore.rs:27,474-513, counted before each attempt). Optiga enforces the cap in-chip (per-attempt counters reset only on correct password). ATECC units weaker: no per-attempt chip counter — cap relies on MCU SmartEEPROM, backstopped by the 730,500-use lifetime KDF budget (atecc.c:64-65,620-621). No MCU-only fallback exists on either device (decryption keys require chip-internal secrets).

H4 — Malicious "change" output: Refuted for both

  • Trezor: change address re-derived from the device seed — host-supplied address discarded (bitcoin.py:966-977); strict script-type/path/multisig-fingerprint matching; everything else + fee confirmed. Residual: multisig config host-supplied each time, shown at GetAddress (all xpubs) but never stored/registered — receive-time defense is out-of-band xpub verification.
  • BitBox02 (stronger): change payload computed on-device from keypath only (signtx.rs:911-946); multisig registration mandatory — signing with an unregistered config fails (signtx.rs:439-441); registration confirms every cosigner xpub on-device and stores it (multisig.rs:167-278).

H5 — ETH blind signing: Partial for both — BitBox02 worse

  • Trezor: clear-signing engine with vendor-CoSi-signed ERC-7730 definitions; built-in ERC-20 approve/transfer with explicit "unlimited" warning (clear_signing.py:373-395). But setApprovalForAll not built in → blind-signed; unknown calldata = skippable raw hex + keccak digest; >6144 B → no clear signing; EIP-712 structural but field metadata unsigned (host-renameable).
  • BitBox02: only ERC-20 transfer decoded (sign.rs:121-145); approve/permit/swaps raw-hex blind-signed with truncation to ~321 chars (ethereum.rs:33-40); token metadata mainnet-only. EIP-712 fully structural (every domain/message member shown) — the one area it leads.

H6 — Backup: BitBox02 confirmed ✔ / Trezor partial

BitBox02 ✔: plaintext backup (backup.rs:219) + restore requires only a new password, never the original (restore.rs:58-61); backup file kept afterward. The microSD card alone is the seed — anyone holding it (or its files via a compromised PC/card reader) recovers the seed with zero on-device interaction. Deliberate design (nothing extra to forget); must be guarded exactly like a written seed phrase. Card is also flash media — unpowered retention is years, not decades; not an archival medium.

Trezor: no write-then-read-back of the mnemonic during setup (BitBox02 does this and wipes on mismatch); integrity instead via per-entry ChaCha20-Poly1305 AEAD + global HMAC chain, corruption → fault-halt/wipe, not silent degradation (storage.c:1511-1537, 1823-1838).

H7 — RNG exposure: Trezor (by design) / BitBox02 not a vuln

  • Trezor: GetEntropy ships strong-mixed RNG to host after on-device confirmation, ≤1024 B, no rate limit beyond the button press. Surfaced additionally: GetNonce returns 32 B of fast RNG with NO confirmation (get_nonce.py:7-15) — THP session use; minor.
  • BitBox02: bootloader raw-TRNG bytes are an anti-glitch canary for ECDSA verification (a "verify" that succeeds on random garbage = glitched verify routine → reject), not a challenge-response; a broken canary cannot admit unsigned firmware (bootloader.c:531-543, 603-615). Re-confirms the systemic zero-health-test finding, bootloader included.

H8/H9 — Storage & factory randomness: Partial for both

  • BitBox02 storage: verified write-back + encrypt-then-MAC solid; but everything that matters (salt root, encrypted seed) is single-copy in one 8 kB chunk — localized corruption = bricked wallet; HMAC mismatch treated as wrong password → 10-try decryption oracle + forced-wipe DoS for a flash-flipper.
  • BitBox02 factory randomness (3rd entropy source, 0xDFE0): deliberately unsigned (per-device) but BOOTPROT-fuse + debug-lockout + stage0 preserve-and-verify-on-reinstall mean host/firmware can't change it. Hygiene flags: a fixed dev constant .bin ships in-repo (scripts/bb02-set-factory-randomness.bin — production must never reuse it); power-loss during stage1 reinstall could silently leave it 0xFF… (no boot-time detection).
  • Trezor attestation: three independent per-device chains — Optiga ECC, TROPIC01 ECC, MCU ML-DSA (post-quantum) — over host challenge; cloning requires invasive per-unit extraction (authenticate_device.py:9-126).

5 · Trezor Model One in a multisig setup

Verdict: yes — with the right configuration, multisig is the best way to keep a Model One in service. It converts the device's worst single-device weaknesses into 1-of-m failures. Verified legacy specifics and their interaction with multisig:

Model One weakness (verified)Neutralized by multisig?
No secure element → physical extraction (voltage-glitch flash readout publicly demonstrated; modern firmware encrypts storage with a PIN-stretched key, but ≤9-digit PIN is offline-brute-forceable)Mostly attacker gets 1 of m keys. Strong passphrase mandatory — never stored, so extraction yields nothing usable.
Single-source entropy (legacy/rng.c: MCU TRNG + repeat-check only, no SE mixing — weakest entropy story reviewed)Yes a weak T1 key is only 1 of m; the Coldcard attack was practical because it was single-sig.
No anti-rollback (old signed firmware flashable; storage wiped but flashable)Yes worst case yields 1 key; wipe makes it noisy.
No anti-exfil, deterministic nonces, no verify-after-sign (shared trezor-crypto path)Partially compromised T1 firmware can exfiltrate its own key (funds still safe) but can also display a fake transaction — fixed only by independent verification on another cosigner.
Older codebase; GetAddress shows address only (no cosigner-xpub review like core models)Partially change checks exist (signing.c:1006,1050) but receive verification is weaker than newer devices.

Multisig does not protect against: receive-address/xpub substitution (verify on ≥2 devices — the T1's small screen shows only the address); correlated quorum compromise (two Model Ones share every weakness; a Trezor-only quorum shares the no-anti-klepto property); backup co-location.

Recommended configuration: 2-of-3 minimum with the T1 as exactly one key; other keys cross-vendor (Safe 7 + BitBox02 are genuinely complementary given the findings above); strong passphrase on the T1 recorded with its backup; T1 as the geographically-separate backup signer, not the daily driver; verify receive addresses on two devices before large deposits; treat any "re-enter your seed" prompt anywhere as an attack.

6 · Recommendations

For Trezor

  1. Add runtime health tests on SE entropy — extend the Tropic prodtest checks (all-zero/repeat) into a boot-time POST for both Optiga and TROPIC01; consider SP 800-90B continuous tests. (T2)
  2. Implement an anti-exfiltration signing protocol (host-nonce commitment à la BitBox02 / sign-to-contract) for ECDSA and Schnorr; deterministic nonces alone cannot stop a malicious build. (H2)
  3. Add verify-after-sign before returning signatures — cheap FI countermeasure. (H2)
  4. Route ML-DSA attestation randomness through the mixed path. (T3)
  5. Add on-device multisig registration (parity with BitBox02); add read-back verification of the mnemonic at setup; require confirmation for GetNonce. (H4/H6/H7)
  6. Add built-in clear-signing for setApprovalForAll / Permit2. (H5)

For BitBox02

  1. Add SP 800-90B-style startup + continuous health tests on every TRNG — repetition-count / adaptive-proportion on the SAMD51; constant-output detection on the ATECC608B path specifically (erratum history). (B1)
  2. Close the taproot anti-klepto gap; consider refusing non-anti-klepto ECDSA by default (opt-out instead of silent fallback). (H2)
  3. Route Noise keygen through the full mix; make the ATECC-default fallback loud. (B3/B4)
  4. Harden storage: redundant copy or ECC for the seed chunk; distinct tamper handling on HMAC mismatch; boot-time 0xFF… detection on factory randomness; confirm the dev .bin constant can never reach production. (H8/H9)
  5. Decode ERC-20 approve and common drainer calls; reduce blind-hex signing. (H5)

For users of these devices

  1. Treat the BitBox02 microSD card exactly like a written seed phrase — it is the seed, unencrypted. Consider mnemonic-words backup instead/additionally; never insert the card into a computer.
  2. Buy direct from the vendor; complete setup in the official app so attestation is checked; never accept a "pre-set-up" device.
  3. Verify every receive address on the device screen; for multisig, on two devices.
  4. Use a strong passphrase (Trezor One: mandatory given its extraction history).
  5. Keep firmware current — rollback protection on both devices means updates are one-way ratchets for fixed bug classes.
  6. Prefer multisig (2-of-3, cross-vendor) for material amounts; it is the architecture that makes every finding in this report survivable.
  7. Never type a seed phrase into any website or app; the #1 real-world loss vector remains seed phishing, not firmware bugs.

7 · Scope & limitations

  • Source-only review of trezor-firmware@ded1c14 (main) and bitbox02-firmware@c838d7f (master), shallow clones taken 1 Aug 2026. Shipped binaries vs. reproducible builds not verified.
  • Vendor submodules not checked out and therefore not audited: libtropic (TROPIC01 stack), cryptoauthlib (ATECC), optiga-trust-m, secp256k1-zkp, trezor-storage (legacy). SE-internal TRNG behavior is out of scope.
  • No dynamic testing, no hardware/fault-injection testing, no side-channel measurement. Findings about FI/SC are code-level inferences only.
  • Bootloader paths reviewed at hypothesis depth, not exhaustively. Host-side software (Trezor Suite, BitBoxApp) out of scope except the in-repo reference client.
  • Coldcard incident details are as publicly reported/advised as of 1 Aug 2026; Coinkite's full postmortem was pending at review time.
  • This report was produced with agent-assisted code mapping; every verdict marked ✔ had its decisive evidence re-read manually at the cited file:line.
